# Claude指摘からCodex修正までのフロー

## 目的

Claudeのレビュー指摘を、事実確認なしに実装へ流し込まないための工程です。

## 標準工程

```text
Claude
第三者レビュー
↓
ChatGPT
Claude回答の妥当性・優先度・過剰提案を整理
↓
Codex
実リポジトリで事実確認
↓
Codex
採用 / 保留 / 対応不要
↓
ChatGPT
Codex採否判断レビュー
↓
ChatGPT
採用項目のみを対象としたCodex修正プロンプト作成
↓
Codex
採用項目のみ修正
↓
Codex
構文確認・テスト・git diff確認
↓
修正後Claude再レビュー要否判断

├─ 不要
│  ↓
│ ChatGPT
│ 最終作業結果・diffレビュー
│
└─ 必要
   ↓
   ChatGPT
   Claude修正後再レビュー用プロンプト作成
   ↓
   Claude Code
   修正後コード再レビュー
   ↓
   ChatGPT
   Claude再レビュー結果レビュー・整理
   ↓
   新規の有効な指摘があるか判断

   ├─ なし
   │  ↓
   │ ChatGPT
   │ 最終作業結果・diffレビュー
   │
   └─ あり
      ↓
      Codex
      実リポジトリで事実確認
      ↓
      Codex
      採用 / 保留 / 対応不要
      ↓
      今回対応必須の重大項目があるか判断

      ├─ なし
      │  ↓
      │ ChatGPT
      │ 最終作業結果・diffレビュー
      │
      └─ あり
         ↓
         Codex
         今回対応必須の重大項目のみ追加修正
         ↓
         Codex
         構文確認・必要なテスト・git diff再確認
         ↓
         ChatGPT
         最終作業結果・diffレビュー
↓
REVIEW_FIX_TRACKER更新
↓
再利用価値がある場合だけlessons更新
```

## ChatGPTで整理する内容

- 指摘ID
- 優先度
- 指摘内容
- 対象機能
- 対象ファイル
- Claudeの根拠
- 仕様書との関係
- 過剰提案の可能性
- Codexに確認させる事項

## Codexで事実確認する内容

- 指摘対象のコードが実在するか
- 指摘条件が実際に発生するか
- 仕様書と矛盾していないか
- 既存実装の意図と衝突しないか
- 影響範囲が依頼範囲内か
- 最小変更で対応できるか
- テストまたは構文確認が可能か

## Codex採否判断後のChatGPTレビュー

Codexが採用 / 保留 / 対応不要を判断した後、修正プロンプトを作る前にChatGPTで採否判断を確認します。

確認する内容:

- 採用項目が確定仕様、既存構造、依頼範囲に合っているか
- 保留項目が仕様判断、DB確認、本番環境確認などを必要とする内容か
- 対応不要項目が誤指摘、仕様上問題なし、依頼範囲外、過剰提案として妥当か
- 採用項目だけに修正対象が限定されているか
- 修正後に必要な確認コマンドが明確か

## 採否区分

| 区分 | 意味 |
| --- | --- |
| 採用 | 事実確認済みで、仕様・既存構造・依頼範囲に合う |
| 保留 | 仕様判断、DB確認、本番環境確認などが必要 |
| 対応不要 | 誤指摘、仕様上問題なし、依頼範囲外、過剰提案 |

## 修正後Claude再レビュー要否判断

Codexが採用項目を修正し、構文確認・テスト・git diff確認を終えた後、修正後Claude再レビューが必要か判断します。

コメント、typo、文言、ドキュメントのみで挙動に影響しない修正は、理由を残したうえで省略できます。

PHPロジック、SQL / DB、認証、認可、SESSION、CSRF、API、メール、cron / CLI、個人情報、token、ファイル操作、JSON生成、複数ファイル、セキュリティに関わる修正では、原則としてClaude Codeへ修正後再レビューを依頼します。

修正後再レビューへ渡すもの:

- 初回Claudeレビューの指摘
- ChatGPTによる指摘整理
- Codexによる事実確認
- Codexの採用 / 保留 / 対応不要判断
- 採用した指摘
- Codexの修正内容
- 対象ファイル
- 修正後git diff
- 構文確認・テスト結果

確認範囲は、前回指摘、Codex採否、採用項目、修正内容、修正後diff、確認結果に限定します。修正後再レビューは、新しい全面設計レビューではありません。

## 修正後再レビューで新しい指摘が出た場合

新しい指摘は直接実装せず、ChatGPTで整理し、Codexが実リポジトリで事実確認してから採否を判断します。

| 区分 | 判断目安 |
| --- | --- |
| 採用候補 | 今回の修正で新しく入った不具合、初回指摘の修正漏れ、確定仕様違反、セキュリティ上重大な問題、Critical / High相当の問題 |
| 保留候補 | 既存不具合の可能性が高い、依頼範囲外、仕様判断が必要、DBまたは本番環境確認が必要 |
| 対応不要候補 | リファクタリング提案、コーディングスタイルの好み、仕様上の問題が確認できない、誤指摘または過剰提案 |

今回追加対応するのは、採用候補の中でも今回対応必須の重大項目に限定します。既存問題、依頼範囲外、大規模リファクタリング案、コーディングスタイルの好み、仕様上問題のない提案、過剰提案は原則として今回の追加修正対象にせず、必要に応じてREVIEW_FIX_TRACKERへ保留として記録します。

追加修正を行った場合は、ChatGPT最終作業結果・diffレビューへ進む前に、Codexで構文確認、必要なテスト、git diff再確認を行います。

## 無限ループ防止

標準工程では、Claude Codeレビューは初回第三者レビューと修正後再レビューの最大2段階までとします。

修正後再レビューを受けて追加修正した場合も、機械的な3回目のClaudeレビューは標準工程に追加しません。追加確認は、重大な未解決問題が残る場合のみ検討します。

## REVIEW_FIX_TRACKERへの記録

指摘は `../review/REVIEW_FIX_TRACKER.md` に記録します。

記録時は、Claudeの指摘内容だけでなく、Codexによる事実確認、対応方針、採否、対応結果、修正後再レビュー結果、最終状態を残します。

## lessonsへの記録

lessonsへ残すのは、再発しやすい問題、AIが誤認しやすい仕様、複数機能で再利用できる知見に限定します。

単発の修正結果はlessonsへ書きません。
