出勤お知らせメールシステム フェーズ別実装手順書

作成日：2026年7月30日

============================================================
1. 実装原則
============================================================

・旧システムを稼働させたまま新システムを構築する。
・各フェーズを独立してテストする。
・前フェーズの完了条件を満たすまで次へ進まない。
・初期状態ではメールを実送信しない。
・DB更新と外部メール送信を同一トランザクションに含めない。
・共通処理をWeb、空メール、管理画面で重複実装しない。
・旧DBは本番切替完了まで変更しない。
・ロールバック不能な変更を一度に行わない。
・各フェーズで修正ファイル、SQL、テスト結果を記録する。

フェーズ1：新DBテーブル作成
============================================================

目的

新システムのデータ基盤を、旧システムへ影響を与えずに追加する。

実施内容

1. 正式DDLをステージングDBへ適用する。
2. SHOW CREATE TABLEで結果を保存する。
3. 外部キーを確認する。
4. UNIQUE制約を確認する。
5. CHECK制約を確認する。
6. 本番DBへ同じDDLを適用する。
7. 本番ではデータをまだ投入しない。

確認SQL

SHOW TABLE STATUS LIKE 't_notification_%';

SHOW CREATE TABLE t_notification_subscriber;
SHOW CREATE TABLE t_notification_subscription;
SHOW CREATE TABLE t_notification_token;
SHOW CREATE TABLE t_notification_event;
SHOW CREATE TABLE t_notification_delivery;
SHOW CREATE TABLE t_notification_suppression;
SHOW CREATE TABLE t_notification_audit_log;

テスト

・同じメールアドレスを2件登録できない
・同じ登録者・店舗・女の子を重複登録できない
・存在しないsubscriber_idで購読登録できない
・不正なstatusを保存できない
・登録者削除時に購読が削除される
・配信履歴がある購読を不用意に削除できない

完了条件

・全テーブルがInnoDB
・全テーブルがutf8mb4
・外部キーが有効
・UNIQUE制約が有効
・テストデータ削除済み
・旧テーブルに変更なし

8. NOTIFICATION_SEND_ENABLED=true
9. 少数のテスト購読で送信する。
10. 件名、本文、リンク、解除を確認する。
11. 全キュー送信を開始する。
12. 送信件数、失敗件数を監視する。

切替直後の監視

・二重配信
・送信漏れ
・受信停止時間

・DBエラー

・二重配信がない
・解除リンクが機能する
・重大エラーがない
・運用担当者が管理画面を確認できる
