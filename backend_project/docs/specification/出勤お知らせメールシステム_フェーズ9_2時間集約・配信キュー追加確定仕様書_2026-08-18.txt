## 7. delivery正式単位

schedule_update deliveryの正式単位：

```text
1 row = 1 event × 1 subscription
```

これは既存DDLの以下と整合する。

```text
UNIQUE(event_id, subscription_id)
```

schedule_updateでは以下を正本とする。

```text
event_id IS NOT NULL
subscription_id IS NOT NULL
```

同一メールにまとめる場合でも、eventごとのdelivery rowは全件作成する。

## 8. message_group_key

`message_group_key` の正式役割：

```text
同一message_group_key = Phase10 senderが1通として送信するschedule_update delivery群
```

mail-group専用tableは追加しない。

`message_group_key` は `BINARY(16)` とし、フェーズ9で以下により生成する。

```text
random_bytes(16)
```

UUID文字列をそのまま保存しない。hash truncationも不要とする。

## 9. message_group_key生成単位

正式単位：

```text
1回のPhase9 claimed batchで処理するevent集合のうち、
同一subscriberへ展開されるschedule_update delivery群
```

つまり以下の組み合わせごとに1つの `message_group_key` を生成する。

```text
Phase9 claimed batch
+
subscriber
```

固定2時間wall-clock window IDにはしない。

cron停止後に回収された古いpending eventも、そのPhase9 batchでclaimされた場合は、そのbatchのsubscriber groupへ含める。

次回batchへ回ったeventは、同じsubscriberであっても別 `message_group_key` とする。

## 10. group invariant

```text

```

```text
1 message_group_key = 1通
```

フェーズ9では、不完全groupを正常commitしない。

## 11. 2時間集約の意味

「2時間」はcron実行間隔を意味する。

event抽出を直近2時間だけに限定しない。

```text
直近2時間だけの検索
```

cron停止や一時障害があっても、未処理pending eventを次回実行で回収する。

固定2時間wall-clock windowを `message_group_key` へ使用しない。

## 17. event lifecycle

既存DDLの状態値を正本とする。

```text
pending
processing
processed
failed
cancelled
```

`pending`：

Phase8生成直後。Phase9対象。

`processing`：

Phase9 claimed batch transaction内での処理中状態。

`processed`：

Phase9 delivery展開完了。対象delivery 0件の場合もprocessed。

`failed`：

Phase9処理が規定回数失敗し、max_attemptsへ到達したevent。

`cancelled`：

Phase9通常処理では原則使用しない。既存DDL上の予約／取消用途を維持する。

## 18. processing / lock列

Phase9では既存event worker系columnを利用可能な範囲で使用してよい。

ただしP0では以下を主機構とする。

```text
advisory lockによるCLI単一起動
+
claimed batch transaction
```

processing状態を長時間commitしたまま外部処理する設計にはしない。

`locked_at`、`locked_by` はclaim識別／運用情報として利用可能だが、P0でstale processing recoveryの必須正本にはしない。

transaction rollback時にはclaim変更もrollbackする。

## 19. batch failure

batch処理途中で例外が発生した場合はROLLBACKする。

以下はcommitしない。

```text
部分delivery
event processed
不完全message group
```

「batch全体失敗」とは、batch transaction全体をROLLBACKするという意味である。

batch内event全件をfailed状態へ変更する意味ではない。

## 20. poison event

1 eventの異常で同じbatchの正常eventが永久停止しないようにする。

正式方針：

原因eventが明確に特定できる場合：

```text
main batch rollback後、
そのeventだけfailure attemptを別transactionで更新する。
```

原因eventが特定できない場合：

```text
batch全件を失敗扱いにしない。
event単位または縮小sub-batchで再評価し、
原因eventを隔離する。
単一event処理でも再現したeventについてのみfailure attemptを更新する。
正常eventは後続の安全なbatchで処理可能にする。
```

## 21. failure attempt

既存DDLの以下を使用する。

```text
attempt_count
max_attempts
failed_at
last_error
status
```

存在しないcolumnを仕様へ追加しない。

失敗記録は、main batch rollback後の別transactionで行う。

```text
attempt_count < max_attempts：
status = pendingへ戻し、再試行可能な状態

max_attempts到達：
status = failed
```

`last_error` へ個人情報、メールアドレス全文、生token、session ID、secret等を記録しない。

Phase9 P0では、event展開retry用の独自backoffは設けない。

failure attempt更新後、max_attempts未満なら `status = pending` へ戻す。

Phase9 failure retry目的では `event.available_at` を変更しない。

次回Phase9 runで、再度pending eventとして処理する。

max_attempts到達時は `status = failed` とし、通常pending抽出対象外とする。

Phase9 event展開retryと、Phase10 delivery送信retryは別責務である。

将来的なPhase9 retry backoffはP2改善候補に留め、P0では実装しない。

## 21.1 P9-06 failure owner model

Phase9 deterministic failureは責任主体を以下に分類する。

```text
EVENT
TARGET
SYSTEM
WORK_DATA
INVARIANT / PROGRAMMING
UNKNOWN
```

EVENT / TARGET / SYSTEM等へ安全に分類できないfailureはUNKNOWNとし、batch rollback、failure_not_attributed、event attempt不消費とする。

## 21.2 EVENT owner

EVENTは、event row / event snapshot固有のdeterministic failureである。

例：

```text
unsupported schedule event type
event snapshot validation failure
```

EVENT failureは `EventDataValidationException` として明示的に識別する。

EVENTのみpoison event isolation対象、`recordFailureAttempt`対象、`attempt_count`増加対象とする。

増加後：

```text
attempt_count < max_attempts
→ pending

attempt_count >= max_attempts
→ failed
```

Phase9固有retry backoffは設けない。

event.available_atはfailure retry目的では変更しない。

raw `ValidationException` を一律EVENT扱いしない。

理由：

```text
ValidationExceptionの原因はEVENT、WORK_DATA、INVARIANT / PROGRAMMING等にまたがるため。
```

event ownerを明示できるvalidationのみ `EventDataValidationException` へ変換する。

EVENT validation scope：

```text
schedule_update template_dataのevents[]部分に対するevent固有validationのみ
```

以下のようなinternal generated field由来failureを一律EVENTへ帰責しない。

```text
summary
next_schedules
request_id
message_group_key
created_at
available_at
delivery_base_date
その他internal generated field
```

## 21.3 TARGET owner

TARGETはdelivery target固有のdeterministic failureである。

P0対象：

```text
invalid_timezone
invalid_quiet_hours
```

TARGET failureは `TargetPlanningException` により明示する。

category：

```text
invalid_timezone
invalid_quiet_hours
```

TARGET failure時：

```text
当該targetだけskip
正常targetは処理継続
batch全体rollbackしない
event attempt_countは変更しない
eventは正常にPhase9展開完了後processed
```

以下は行わない。

```text
timezone fallback
subscriber自動修正
subscriber status自動変更
subscription pause
suppression自動追加
target retry table追加
```

timezone / quiet-hoursはsubscriber単位設定である。

同一claimed batch中に1 subscriberがTARGET failureとなった場合、以後同subscriberについて同じTARGET validationを再実行せずskip可能とする。

invalid subscriber setはbatch内一時状態であり、DBへ保存しない。

TARGET failure例：

```text
event A

subscriber A：valid
subscriber B：invalid timezone
subscriber C：valid

結果：

A delivery生成
B skip
C delivery生成
event A processed
attempt_count不変
batch COMMIT
```

TARGET only：

```text
eligible targetは存在するが全targetがTARGET failureの場合、
delivery 0
event processed
attempt_count不変
次回Phase9で再claimしない
```

target data修復後も、processed済みeventについてPhase9が自動遡及delivery生成しない。

zero-targetとの区別：

```text
event_zero_target：
eligible/current target自体が最初から0件

event_all_targets_invalid：
eligible targetは1件以上存在したが全件TARGET failureでskip
```

TARGET counters：

```text
target_invalid_skipped：
TARGET failureによりskipしたevent × subscription target件数

event_all_targets_invalid：
eligible targetが存在したeventのうち、
valid targetが0でTARGET failureによるskipが1件以上存在したevent件数

event_zero_target：
既存意味を変更しない
```

TARGET diagnostics：

```text
最大20samples

fields：
event_id
subscriber_id
subscription_id
shop_id
cast_id
error_category
```

以下はdiagnosticへ含めない。

```text
email全文
token
secret
session ID
```

TARGET skipのみでbatch自体が正常COMMITした場合：

```text
success = true
error_count = 0
exit_code = 0
```

TARGET failure自体をCLI fatal errorとはしない。

counter / diagnosticで運用検知可能にする。

## 21.4 SYSTEM / WORK_DATA / INVARIANT / UNKNOWN

SYSTEM：

```text
PDOException
batch rollback
event attempt不消費
failure_event_idなし
failure_not_attributed
```

`isSystemLevelFailure` はPDOExceptionかどうかで判定し、SQLSTATE個別判定には依存しない。

WORK_DATA：

```text
t_work_list等の参照schedule data由来の異常。
eventへ自動帰責しない。
P0ではWORK_DATA固有skip/retry機構を追加しない。
安全に処理できない場合はbatch rollback、failure_not_attributed、event attempt不消費。
```

INVARIANT / PROGRAMMING：

```text
内部生成値やapplication invariant異常。
eventへ自動帰責しない。
```

UNKNOWN：

```text
EVENT / TARGET / SYSTEM等へ安全に分類できないfailure。
batch rollback。
failure_not_attributed。
event attempt不消費。
勝手にTARGET skipしない。
勝手にevent failed化しない。
```

poison isolationでは、batch rollback後、SYSTEMでなければ各eventを単独で再評価し、EVENT owner failureを再現できたeventのみfailure attempt対象とする。

現在処理中だったevent IDをそのまま犯人として信用しない。

## 28. quiet-hours計算

正式計算：

```text
subscriber local current datetime
↓
quiet interval判定
↓
quiet-hours中ならquiet終了local datetime
↓
UTC変換
↓
delivery.available_at
```

quiet-hours外：

```text
delivery.available_at = Phase9 queue作成時UTC
```

quiet-hours無効：

```text
delivery.available_at = Phase9 queue作成時UTC
```

日跨ぎに対応する。

`DateTimeImmutable` + `DateTimeZone` によるDST対応を前提とする。

## 29. group available_at

同一subscriberの同一 `message_group_key` 内は、同一 `available_at` とする。

理由：

```text
1メールgroup内deliveryが別時刻に送信可能になる状態を作らないため。
```

## 30. 配信予定基準日

旧仕様の曖昧な送信日基準表現をPhase9 snapshotでは直接使用しない。

Phase9正式用語：

```text
配信予定基準日
```

正式定義：

```text
delivery.available_atをsubscriber.timezoneへ変換したcalendar date
```

## 31. 次回出勤日最大3件

次回出勤日最大3件はPhase9でsnapshot固定する。

条件：

```text
schedule_date >= 配信予定基準日
かつ
canonical state = WORK
```

並び順：

```text
schedule_date ASC
```

件数：

```text
最大3件
```

calendar dateごとに最大1件とする。

通常運用では、同一cast / 同一calendar dateに複数source rowが存在することは想定しない。

ただし異常・例外データとして同一calendar dateに複数rowが存在した場合：

```text
ORDER BY win ASC
```

の最初のrowを、そのcalendar dateの代表rowとする。

代表rowをcanonicalizeする。

```text
canonical WORK：
next_schedulesへ追加

WORK以外：
そのcalendar dateはnext_schedulesへ追加しない
```

同日の後続rowは採用しない。

これは正常データモデルとして同日複数rowを許容する仕様ではなく、異常データに対するP0 deterministic fallbackである。

除外：

```text
UNREGISTERED
OFF
TEL
HOLIDAY
LAST
OTHER_SPECIAL
```

Phase9は `ScheduleEventDecisionService::canonicalize()` をread-only再利用してよい。

## 32. Phase10遅延

Phase10 actual sendが `available_at` より遅れ、実際の送信calendar dateが変わっても、`next_schedules` を再計算しない。

Phase9で固定したsnapshotを使用する。

Phase10実送信日を次回出勤日最大3件の基準にはしない。

## 42. batch sizeの意味

batch sizeは、1 Phase9 transactionでclaimする最大event数である。

delivery行数ではない。

subscription数が多い場合、delivery INSERT数はevent数より多くなり得る。

batch上限を超えたpending eventは、次回Phase9 cron executionで回収する。

Phase9はpending backlogをavailable_at順に回収する。

「2時間」はevent発生から直近2時間だけを固定windowで取得する意味ではなく、cron実行間隔が2時間ごとであることを意味する。

## 42.1 P9-05 known inconsistent state

以下をKNOWN INCONSISTENT-STATE BEHAVIORとして記録する。

異常状態：

```text
t_notification_event.status = pending
かつ
同一(event_id, subscription_id)のt_notification_deliveryが既に存在する
```

この場合：

```text
既存deliveryは既存message_group_keyを維持する。

同一subscriberの別event / 別subscriptionに対して
今回新規deliveryが生成されると、
preexisting deliveryとnew deliveryでmessage_group_keyが分かれる場合がある。
```

これは正常Phase9 flowでは生成されない。

正常Phase9では、delivery INSERTとevent processed化を同一claimed batch transactionでcommitする。

したがって、pending event + 既存delivery は以下によってのみ発生し得る異常状態として扱う。

```text
manual DB modification
不完全な手動補修
その他DB inconsistent state
```

P9-05 P0方針：

```text
auto repairしない
既存deliveryのgroup変更禁止
既存delivery削除禁止
pending event自動再構築禁止
新DDL禁止
production code変更不要
運用上の既知異常として記録
```
