# 出勤お知らせメールシステム フェーズ8出勤変更イベント生成追加確定仕様書

作成日：2026-08-12
対象フェーズ：フェーズ8「出勤変更イベント生成」

## 1. 文書目的

本書は、横浜ダンディーグループ「出勤お知らせメールシステム」におけるフェーズ8「出勤変更イベント生成」の追加確定仕様書である。

フェーズ8実装前調査および追加仕様案検討により、schedule状態分類、特殊状態遷移、schedule DELETE、event_type優先順位、event_key、reconciliation、event INSERT失敗時の扱い、日付timezoneについて追加仕様確定が必要と判明した。

本書はそれらを正式に固定し、以後のフェーズ8実装時の最優先正本とする。

本書は仕様を固定するための文書であり、PHP、Next.js、JS、TS、TSX、DDL、DB、config、cron、.procmailrcを変更するものではない。

## 2. 参照優先順位

フェーズ8「出勤変更イベント生成」について、既存資料と本書の内容が競合する場合は本書を優先する。

参照優先順位：

```text

5. 現行実装
```

backup等の旧資料をフェーズ8の根拠として自動採用しない。

## 4. schedule正本

フェーズ8が参照するschedule正本は、既存管理画面側の以下テーブルとする。

```text
t_work_list
```

実DB上の主な性質：

```text
Engine = MyISAM
PKなし
UNIQUEなし
FKなし
```

主な列：

```text
g_id
shop_id
win
wout
brin
brout
wuptime
wait
warea_row
```

`win`、`wout`、`brin`、`brout`、`wuptime` は varchar にUnix timestamp文字列として保存されている。

重要制約：

```text
t_work_list = MyISAM
t_notification_event = InnoDB
```

したがって、既存schedule保存と `t_notification_event` INSERTを単一の完全ACID transactionとして原子的にcommitすることはできない。

## 6. Phase8処理位置

正式な概念フロー：

```text
保存前schedule snapshot取得
↓
既存schedule保存
↓
既存JSON生成
↓
保存後schedule snapshot取得
↓
Phase8判定
↓
event INSERT
```

既存schedule保存や既存JSON生成より前にeventを確定しない。

POST値だけを正本にしない。保存前後のDB値から判定する。

## 7. canonical state

フェーズ8内部判定用canonical stateは以下とする。

```text
UNREGISTERED
WORK
OFF
TEL
HOLIDAY
LAST
OTHER_SPECIAL
```

生の秒コードをevent判定ロジックへ散在させない。

既存DB表現をcanonical stateへ正規化した上で判定する。

## 8. canonical state分類

canonical stateの正式分類：

| canonical state | DB条件・意味 | Phase8分類 |
|---|---|---|
| UNREGISTERED | 対象shop_id + cast_id + schedule_dateについて、通知判定対象となる勤務scheduleが存在しない状態 | 初回WORK化の候補 |
| WORK | 通常の出勤開始・終了時刻を持つ勤務状態 | 通知判定対象 |
| OFF | `win` 秒 `03` 届出休、または `win` 秒 `13` お休み | 休み変更対象 |
| TEL | `win` 秒 `02` または `08` | 通知対象外 |
| HOLIDAY | `win` 秒 `04` の公休日コード | 通知対象外 |
| LAST | `wout` 秒 `09` | 通知対象外 |
| OTHER_SPECIAL | `win` 秒 `05` / `11` / `12` / `14`、および現行表示上 `21`～`25` の出張中特殊状態等 | 通知対象外 |

`UNREGISTERED` は単なるDB行なしだけではなく、現行保存仕様と整合する「勤務実体なし」を含めて実装時に判定する。

## 9. OFF正式定義

フェーズ8で `schedule_changed_to_off` / `schedule_changed_to_work` の対象となるOFFは以下のみとする。

```text
届出休：win秒 = 03
お休み：win秒 = 13
```

したがって、OFFは以下と定義する。

```text
OFF = 届出休 + お休み
```

以下はOFFへ含めない。

```text
TEL
公休日
LAST
その他特殊状態
```

## 10. TEL

TELは以下とする。

```text
win秒 = 02
win秒 = 08
```

フェーズ8では通知対象外とする。

TELがbeforeまたはafterに含まれる遷移ではeventを生成しない。

例：

```text
WORK → TEL   eventなし
TEL → WORK   eventなし
TEL → OFF    eventなし
OFF → TEL    eventなし
```

## 11. HOLIDAY

HOLIDAYは以下とする。

```text
win秒 = 04
```

フェーズ8では通知対象外とする。

HOLIDAYがbeforeまたはafterに含まれる遷移ではeventを生成しない。

例：

```text
WORK → HOLIDAY    eventなし
HOLIDAY → WORK    eventなし
HOLIDAY → OFF     eventなし
OFF → HOLIDAY     eventなし
```

## 12. LAST

LASTは以下とする。

```text
wout秒 = 09
```

フェーズ8では通知対象外とする。

LASTがbeforeまたはafterの通知判定意味に関与する場合もeventを生成しない。

LASTをOFF扱いしない。

## 13. OTHER_SPECIAL

以下等の特殊状態はOTHER_SPECIALとして扱う。

```text
win秒 = 05
win秒 = 11
win秒 = 12
win秒 = 14
win秒 = 21～25（現行表示上の出張中特殊状態）
その他、WORK / OFF / TEL / HOLIDAY / LASTに正式分類されない特殊状態
```

OTHER_SPECIALはフェーズ8通知対象外とする。

21～25は公休日そのものではなく出張中特殊状態として扱い、OFFへもHOLIDAYへも含めない。

OTHER_SPECIALを含む遷移ではeventを生成しない。

## 14. schedule_created

正式条件：

```text
before = UNREGISTERED
after = WORK
```

event_type：

```text
schedule_created
```

OFF → WORKは `schedule_created` にしない。

```text
OFF → WORK = schedule_changed_to_work
```

TEL / HOLIDAY / LAST / OTHER_SPECIAL → WORKはeventなしとする。

## 15. schedule_start_changed

正式条件：

```text
before = WORK
after = WORK
AND
start_timeが変更
```

event_type：

```text
schedule_start_changed
```

終了時刻も同時に変更されていてよい。

例：

```text
10:00～18:00
↓
11:00～19:00

= schedule_start_changed
```

終了時刻だけ変更された場合はeventなしとする。

例：

```text
10:00～18:00
↓
10:00～19:00

= eventなし
```

## 16. schedule_changed_to_off

正式条件：

```text
before = WORK
after = OFF
```

event_type：

```text
schedule_changed_to_off
```

TEL、HOLIDAY、LAST、OTHER_SPECIALへの変更を `schedule_changed_to_off` へ流用しない。

## 17. schedule_changed_to_work

正式条件：

```text
before = OFF
after = WORK
```

event_type：

```text
schedule_changed_to_work
```

TEL、HOLIDAY、LAST、OTHER_SPECIALからWORKへの変更を `schedule_changed_to_work` へ流用しない。

## 18. event判定マトリクス

正式なevent判定マトリクス：

| before | after | event | 理由 |
|---|---|---|---|
| UNREGISTERED | WORK | schedule_created | 初回出勤登録 |
| WORK | WORK（start変更あり） | schedule_start_changed | 出勤開始時刻変更 |
| WORK | WORK（endのみ変更） | eventなし | 終了時刻だけの変更は対象外 |
| WORK | WORK（同一内容） | eventなし | 同一内容再保存は対象外 |
| WORK | OFF | schedule_changed_to_off | 休みへの変更 |
| OFF | WORK | schedule_changed_to_work | 休みから出勤への変更 |
| TELを含む | 任意 | eventなし | TEL確認は対象外 |
| 任意 | TELを含む | eventなし | TEL確認は対象外 |
| HOLIDAYを含む | 任意 | eventなし | 公休日は対象外 |
| 任意 | HOLIDAYを含む | eventなし | 公休日は対象外 |
| LASTを含む | 任意 | eventなし | LASTは対象外 |
| 任意 | LASTを含む | eventなし | LASTは対象外 |
| OTHER_SPECIALを含む | 任意 | eventなし | その他特殊状態は対象外 |
| 任意 | OTHER_SPECIALを含む | eventなし | その他特殊状態は対象外 |
| 任意 | 過去日 | eventなし | 過去日修正は対象外 |
| 休憩のみ変更 | 休憩のみ変更 | eventなし | 休憩は対象外 |
| DELETE | DELETE | eventなし | schedule削除は対象外 |
| realtime | realtime | eventなし | リアルタイム更新は対象外 |

## 19. event生成単位

1保存処理におけるevent生成単位：

```text
shop_id
+
cast_id
+
schedule_date
```

1 schedule_dateについて、1保存につき最大1 eventとする。

同一保存から複数event_typeを生成しない。

## 20. event_type優先順位

1回の保存で複数の差分条件に該当し得る場合の正式優先順位：

```text
1. schedule_created
2. schedule_changed_to_off
3. schedule_changed_to_work
4. schedule_start_changed
```

ただし、canonical state遷移判定により、本来複数該当をできるだけ発生させない設計とする。

## 21. 休憩変更

`brin` / `brout` だけの変更はeventなしとする。

休憩はフェーズ8通知対象外である。

start_time変更と同時に休憩が変わった場合は、start_time変更判定を妨げない。

## 22. schedule DELETE

`delete_work_time()` によるschedule row削除はフェーズ8event対象外とする。

削除を `schedule_changed_to_off` と推測しない。

理由：

```text
schedule row削除
お休み／届出休への変更
```

は業務上同義とは限らないため。

現在の4 event_typeへ削除専用typeを追加しない。

## 23. 過去日

以下の場合はeventなしとする。

```text
schedule_date < Asia/Tokyo基準のtoday
```

過去日の修正は通知対象外である。

## 24. timezone

timezone責務を以下のように分離する。

```text
schedule_dateの当日判定 = Asia/Tokyo calendar date
通知DB timestamp = UTC
```

UTC timestampの対象：

```text
occurred_at
created_at
available_at
updated_at
processed_at
failed_at
```

フェーズ8のために以下を変更しない。

```text
GLOBAL timezone
SESSION timezone
```

schedule_dateとDB timestampのtimezone責務を混同しない。

## 25. t_notification_event

正式DDLは以下とする。

```text
backend_project/docs/specification/DDL/fase1_DB_table_DDL_2026-08-03.sql
```

正式event_type：

```text
schedule_created
schedule_start_changed
schedule_changed_to_off
schedule_changed_to_work
```

正式source_type：

```text

```

Phase8 direct生成では以下を使用する。

```text

```

Phase8ではreconciliationを実装しないため、`source_type = reconciliation` は将来互換としてDDL上維持する。

## 26. Phase8 payload

`before_payload` / `after_payload` は、通知eventの意味を説明可能な必要最小schedule snapshotとする。

canonical payloadの基本：

```text
state
start_time
end_time
special_code
```

例：

```json
{
  "state": "WORK",
  "start_time": "10:00",
  "end_time": "18:00",
  "special_code": null
}
```

payloadへ原則重複保存しない項目：

```text
shop_id
cast_id
shop_name
cast_name
schedule_date
```

これらはトップレベル列またはsnapshot列を使用する。

payloadへ含めない項目：

```text
subscriber
subscription
email
token
secret
```

Unix timestamp生値より、canonical stateおよび `HH:MM` 等の正規化値を使用する。

## 27. payloadのstate

payloadの `state` は以下のcanonical値を使用する。

```text
UNREGISTERED
WORK
OFF
TEL
HOLIDAY
LAST
OTHER_SPECIAL
```

通知eventを生成しない特殊状態についても、判定内部ではcanonical state化してよい。

## 28. shop_name_snapshot / cast_name_snapshot

event作成時点の正式名称snapshotを保存する。

取得元は既存の正式DBまたはRepository方式を使用する。

Phase8独自の名称変換を作らない。

## 31. subscriptionとの責務分離

Phase8はschedule event生成までを担当する。

以下はPhase8で判定しない。

```text
subscriber status
subscription status
suppression
delivery対象
```

active subscriptionが0件でも、通知対象schedule changeであればevent自体は生成する。

Phase9が購読およびdelivery対象抽出を担当する。

## 32. 公開状態との責務分離

Phase7公開状態同期をPhase8へ混在させない。

Phase8はschedule変更事実をevent化する。

Phase8自身が以下を行わない。

```text
subscription pause
subscription restore
delivery cancellation
```

公開状態による最終配信可否は、Phase7、Phase9、後続senderの責務と分離する。

## 33. failure isolation

`t_work_list` がMyISAMであるため、schedule保存とevent INSERTを単一の完全ACID transactionにはしない。

正式方針：

```text
1. 既存schedule保存
2. 既存JSON生成
3. Phase8 event生成
```

event INSERT失敗時：

```text
既存schedule保存成功を維持
既存JSON成功を維持
管理画面成功フローを阻害しない
Phase8処理のみ失敗
operational ERROR log
管理画面警告UI追加なし
```

2026-08-18時点のfailure isolation確認範囲：

```text
DB-layer event INSERT failure isolation PASS
management hook failure isolation static確認 PASS
通常ブラウザ回帰 PASS
forced event INSERT failure browser E2Eは未実施
```

現在のPhase8完了条件では、DB-layer isolationとstatic hook確認をPhase8 failure isolation確認として採用済みである。

forced failure browser E2Eを新しいmandatory testとして追加しない。


以下を含めない。


## 35. reconciliation

重要な仕様変更として、既存概要仕様にあった以下はPhase8では実装しない。

```text
イベント生成漏れを照合ジョブで補完する
```

理由：

```text
t_work_listは最新状態のみ
schedule履歴tableなし
変更前snapshotを後から復元できない
wuptimeは完全なchange revisionではない
```

したがって、現在状態から過去の通知対象変更を安全に再構築できない。

## 36. reconciliation保留

Phase8では以下のみ実装対象とする。

```text
direct schedule event generation
```

以下は保留する。

```text
event漏れ完全復元reconciliation
```

現在状態から過去変更を推測してeventを自動生成してはならない。

## 37. reconciliation将来対応

将来、完全なevent reconciliationを実装する場合は、別途以下等の履歴基盤を検討する。

```text
schedule change ledger
outbox
revision ID

```

ただし、本Phase8では以下とする。

```text
新table追加なし
DDL追加なし
```

## 38. wuptime

`wuptime` をPhase8の正式change revisionとして使用しない。

理由：

```text
秒精度
同一秒複数保存を区別不能
複数日更新で同値になり得る
DELETEには残らない
履歴IDではない
```

event_keyの一意change identityとして `wuptime` へ依存しない。

## 39. event_key

event_keyのDB仕様：

```text
BINARY(32)
SHA-256
UNIQUE
```

既存 `NotificationEventService::eventKeyHash()` は利用可能である。

ただし、現行データ構造には完全なchange revisionが存在しない。

そのためPhase8 direct-only実装では、event_keyは以下を目的とする。

```text
同一保存処理内の二重event INSERT防止
同一logical event生成処理の再呼び出し防止
```

## 40. event_keyの限界

以下の例では、1回目と3回目は同一before/afterでも別の業務変更である。

```text
10:00 → 11:00
↓
11:00 → 10:00
↓
10:00 → 11:00
```

現行DBだけで、これらを完全に一意なchange revisionとして識別することはできない。

したがって、以下の設計は禁止する。

```text
過去に同じbefore/afterが存在した場合も永久に同じevent_keyへする
```

一方、信頼できる永続revisionがない以上、完全な再発識別保証もPhase8では行わない。

## 41. event_key request identity調査結果

既存schedule保存処理には、Phase8のchange revisionとして安全にそのまま使用できる永続request identity / revision IDは存在しなかった。

以下はPhase8 event_keyのchange identityとして使用しない。

```text
wuptime
time()単独
保存開始時刻単独
```

追加DDLは行わない。

## 42. event_key最終実装

Phase8ではHTTP保存request単位で `RequestId::generate()` によりrequest-scoped request_idを1つ生成する。

同一HTTP保存リクエスト内では、対象cast / schedule_dateが複数でも同じPhase8 request_idを共有する。

event_key canonical material：

```php
[
    'version' => 'phase8-v1',
    'request_id' => $phase8RequestId,
    'shop_id' => $shopId,
    'cast_id' => $castId,
    'schedule_date' => $scheduleDate,
    'event_type' => $eventType,
    'before' => [
        'state' => $beforeState,
        'start_time' => $beforeStartTime,
        'end_time' => $beforeEndTime,
        'special_code' => $beforeSpecialCode,
    ],
    'after' => [
        'state' => $afterState,
        'start_time' => $afterStartTime,
        'end_time' => $afterEndTime,
        'special_code' => $afterSpecialCode,
    ],
]
```

SHA-256生成：

```text
NotificationEventService::eventKeyHash()
```

正式保証範囲：

```text
同一保存処理内の二重INSERT防止
同一logical event処理の再呼び出し防止
```

保証しない範囲：

```text
完全並行した別HTTP request間のlogical duplicate完全排除
```

追加DDL：

```text
なし
```
