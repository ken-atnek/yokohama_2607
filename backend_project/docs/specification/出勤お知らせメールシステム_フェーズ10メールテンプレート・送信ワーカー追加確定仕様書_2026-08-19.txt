============================================================
4. Phase10 batch size
============================================================

1 Phase10 CLI invocationは、最大100 mail unitsを処理する。

「100件」はdelivery row数ではない。

```text
schedule_update:
最大100 message groups

その他mail:
1 delivery row = 1 unit
```

1 message_group_keyに150 delivery rows存在しても、1 mail unitとして扱う。

100 rows + 50 rowsへ分割してはならない。

Phase10正式config候補：

```text
notification_send_batch_size
default = 100
P0 max = 100
未定義 / 不正値 = 100
```

actual configへの追加はPhase10 implementation時に行う。本書作成時点ではconfigを変更しない。

============================================================
5. claim処理単位
============================================================

100 mail unitsを先に全件sending化しない。

1 mail unitごとに以下を完了してから次mail unitへ進む。

```text
claim
↓
send
↓
outcome update
```

1 invocation内で最大100回繰り返す。

理由：

100 mail unitsを先行claim後にworker crashすると、最大100 mail unitsがsend outcome unknownになり得るため、ambiguous範囲を1 mail unitへ限定する。

============================================================
6. eligible delivery
============================================================

Phase10 claim対象：

```text
status IN ('queued', 'deferred')
AND available_at <= current UTC
```

schedule_update mail unitがPhase10処理candidateとなる条件：

```text
同一message_group_key内に1件以上、
status IN ('queued', 'deferred')
AND available_at <= current UTC
を満たすdelivery rowが存在すること。
```

schedule_updateでは、representative row自身がqueued / deferredであることをcandidate条件にはしない。

対象外：

```text
sending
sent
failed
suppressed
cancelled
```

============================================================
7. multi-worker / representative
============================================================

Phase10はmulti-worker対応を想定する。

`FOR UPDATE SKIP LOCKED` をP0候補として採用する。

ただし、schedule_updateについて単純row claimは禁止する。

同一message_group_key内の別rowをworker A / worker Bが別々にcandidateとして取得すると、`1 group = 1 mail` が壊れる。

そのため `mail unit representative` を定義する。

```text
schedule_update:
candidateとなったgroupについて、group全体のMIN(delivery_id)等のdeterministic rowをrepresentativeとする。
representative row自身がqueued / deferredであることをcandidate条件にはしない。

その他mail:
delivery_id自身。
```

representativeをclaimしたworkerだけが、そのmail unit全rowを処理する。

同一message_group_keyについて、複数workerが別rowを別mail unitとして取得してはならない。

representative取得後の要件：

```text
group全row lock
↓
group invariant validation
↓
group全row sending化
```

正確なSQLはPhase10 implementationで確定する。

仕様上は、同一message_group_keyを複数workerへ分割claimしないことを必須invariantとする。

この分離により、以下の異常groupもcandidateとして検出し、group invariant validationへ到達させる。

```text
delivery 100 = sent
delivery 101 = queued
same message_group_key
```

上記はrepresentative rowがsentであっても、group内にeligible rowが存在するためcandidateとなる。

============================================================
8. claim transaction
============================================================

1 mail unitについて以下を同一transactionで行う。

```text
BEGIN
↓
representative claim
↓
mail unit全row lock
↓
group invariant validation
↓
status = sending
↓
locked_at設定
↓
locked_by設定
↓
attempt_count += 1
↓
token付きmailならtoken生成
↓
token_hash INSERT
↓
expires_at確定
↓
COMMIT
```

COMMIT後に以下を行う。

```text
render
↓
mail send
```

送信中にDB transactionを保持しない。

============================================================
9. attempt_count / max_attempts
============================================================

`attempt_count` の正式意味：

```text
Phase10送信試行開始回数
```

送信成功回数ではない。

mail()関数が実際に呼ばれた回数と完全同義ではない。

mail unitをsendingへclaimし、claim transactionがCOMMITして1回の送信試行を開始した時点で1 attemptを消費する。

increment：

```text
mail unitをsendingへclaimするtransaction内
```

理由：

renderer failure、transport definite failure、mail送信後のDB sent更新失敗、worker crash等も、Phase10送信試行として記録する必要があるため。

`max_attempts` の正式意味：

```text
初回を含む総Phase10送信試行数
```

DDL defaultの5を維持する。

```text
max_attempts = 5
attempt 1 = 初回
attempt 2〜5 = retry
総Phase10送信試行 = 5
retry回数 = 4
```

============================================================
10. retry interval
============================================================

Phase10 P0 retry interval：

```text
attempt 1 failure: 5分後  / 300秒
attempt 2 failure: 15分後 / 900秒
attempt 3 failure: 1時間後 / 3600秒
attempt 4 failure: 6時間後 / 21600秒
attempt 5 failure: failed
```

既存資料に例示されていた24時間間隔案は採用しない。

理由：

```text
max_attempts = 5 = 総5 Phase10送信試行
```

と矛盾するため。

DDL defaultは変更しない。

============================================================
11. definite transport failure
============================================================

mail transportが同期的にfalseまたは明示的exceptionを返した場合、`definite send failure` として扱う。

Phase10 P0ではtemporary / permanentを推測しない。

```text
attempt_count < max_attempts:
status = deferred
available_at = current UTC + retry delay
deferred_at設定
locked_at / locked_by clear
last_errorを安全に保存

attempt_count >= max_attempts:
status = failed
failed_at設定
locked_at / locked_by clear
```

12. Phase12境界
============================================================

以下はPhase10同期send resultから推測しない。

```text
hard bounce
invalid recipient
complaint
その他非同期恒久failure
```

これらはPhase12 suppression責務である。

============================================================
12.1 render_failure
============================================================

正式diagnostic code：

```text
render_failure
```

定義：

```text
mail unit claim COMMIT後、mail transportを呼び出す前のrenderer処理で発生したdeterministic failure。
```

例：

```text
template_data_snapshot不正
必須placeholder不足
unsupported mail_type renderer
renderer internal validation failure
mail()呼出前に本文生成を完了できないfailure
```

render_failure時はmail transportを呼び出していない。

したがってsend_outcome_unknownではなく、利用者へ届いた可能性はない。

token付きmailの場合は、そのattemptで発行したtokenをrevokeする。

```text
attempt_count < max_attempts:
status = deferred
available_at = current UTC + retry delay
deferred_at設定
locked_at / locked_by clear
last_error_code = render_failure

attempt_count >= max_attempts:
status = failed
failed_at設定
locked_at / locked_by clear
last_error_code = render_failure
```

次回retryでは新tokenを生成する。

retry intervalは通常のPhase10 retry intervalを使用する。

============================================================
13. group outcome invariant
============================================================

schedule_update groupでは、全rowが同じ送信試行を共有する。

したがって以下はgroup全row同時遷移とする。

```text
sending
sent
deferred
failed
```

sent：

```text
group全row status = sent
sent_at同一
locked_at NULL
locked_by NULL
last_error clear
```

deferred：

```text
group全row status = deferred
available_at同一
deferred_at同一
attempt_count同一
locked clear
```

failed：

```text
group全row status = failed
failed_at同一
attempt_count同一
locked clear
```

============================================================
14. claim count validation
============================================================

Phase9のclaim count mismatch patternをPhase10でも採用する。

mail unit全rowについて、期待row数と実UPDATE row数が一致しない場合は正常sendへ進まない。

その場合はtransaction rollbackする。

============================================================

正式diagnostic code：

```text

```

異常状態例：

```text
同一message_group_keyに sent / queued が混在
attempt_count不一致
available_at不一致
max_attempts不一致
template_key不一致
template_version不一致
recipient_email_snapshot不一致

```

正式同一性確認候補：

```text
subscriber_id
recipient_email_snapshot
mail_type
available_at
status
attempt_count
max_attempts
template_key
template_version
```

P0方針：

```text
auto repairしない
既にsentのrowは変更しない
未送信rowは status = failed
last_error_code = group_invariant_violation
manual review対象
```

単純skipして毎回workerへ再検出させない。

既sent rowをqueued等へ戻さない。

既sent rowを再送しない。

============================================================
16. token responsibility
============================================================

token付きmailは以下とする。

```text
verify_email
settings_link
```

これらのtokenはPhase10送信試行直前に生成する。

Phase4 / Phase6 queue作成時にはraw tokenを生成しない。

token generation：

```text
$rawToken = bin2hex(random_bytes(32));

rawToken:
64文字小文字hex

$tokenHash = hash('sha256', $rawToken, true);

token_hash:
BINARY(32)

DBにはSHA-256 hashのみ保存
raw tokenはprocess memoryのみ
```

verify_email / manage_settingsでは同じtoken representationを使用する。

禁止：

```text
raw token DB保存
raw token delivery snapshot保存
raw token log出力
```

16.1 token INSERT contract
------------------------------------------------------------

verify_email：

```text
subscriber_id = delivery.subscriber_id
subscription_id = delivery.subscription_id
purpose = verify_email
subscription_id NOT NULL
token_hash = SHA-256(rawToken) binary
expires_at = token INSERT UTC + 3600 seconds
```

manage_settings / settings_link：

```text
subscriber_id = delivery.subscriber_id
subscription_id = NULL
purpose = manage_settings
token_hash = SHA-256(rawToken) binary
expires_at = token INSERT UTC + 3600 seconds
```

上記はDDL chk_tntk_targetと整合させる。

============================================================

```text

```

理由：

```text

```

============================================================

```text

```


20. definite send failure token
============================================================

明示的なtransport failure時は、そのattemptで生成したtokenをrevokeする。

token revokeとdelivery deferred / failed更新を同一outcome transactionで行う。

次回retryでは新tokenを生成する。

============================================================
21. send outcome unknown
============================================================

正式diagnostic code：

```text
send_outcome_unknown
```

定義：

```text
mailが送られた可能性があるが、送信成功をDBへ確定記録できなかった状態
```

例：

```text
mail transport success -> sent UPDATE failure
mail transport success -> worker crash
send call中または直後にworker process消失
```

P0方針：

```text
automatic retryしない
即terminal
status = failed
last_error_code = send_outcome_unknown
manual review対象
max_attempts到達を待たない
```

============================================================
21.1 failure boundary
============================================================

render_failure：

```text
mail transport呼出前
確実に未送信
retry可
token revokeあり
send_outcome_unknownへ分類しない
```

transport_failure：

```text
mail transportが同期的にfalseまたは明示的definite failureを返した状態
retry可
token revokeあり
send_outcome_unknownへ分類しない
```

send_outcome_unknown：

```text
mailが送られた可能性があるがDBへsuccessを確定できない状態
automatic retry禁止
token revokeなし
terminal failed
```

============================================================
22. outcome unknown時token
============================================================

send outcome unknownではtokenを自動revokeしない。

理由：

実際に利用者へメールが届いている可能性があり、自動revokeすると届いた認証URLを無効化する危険があるため。

outcome unknown時tokenは以下の通常life cycleへ任せる。

```text
used
expires_at
manual revoke
```

verify_email：

```text
届いていたmailから正常認証可能
```

settings_link：

```text
届いていたmailのtokenを有効期限内は利用可能
```

============================================================
23. stale sending
============================================================

stale sendingはsend outcome unknownと同一分類とする。

```text
automatic retryしない
status = failed
last_error_code = send_outcome_unknown
manual review対象
```

============================================================
24. stale threshold
============================================================

Phase10 P0正式値：

```text
30分
1800秒
```

これは旧backup値の採用ではなく、Phase10 P0の新規仕様値である。

判定：

```text
status = sending
AND locked_at <= current UTC - 1800 seconds
```

理由：

通常mail send処理は長時間DB lockを保持しない設計である。

一方、stale判定後は自動retryではなくsend_outcome_unknownとしてterminal化するため、生存中workerを早すぎるthresholdで誤判定しないよう余裕を持った値を採用する。

Phase10正式config候補：

```text
notification_send_stale_threshold_seconds
default = 1800
未定義 = 1800
```

minimum / maximumの厳密値はimplementation時に安全なvalidationを設定する。

本書作成時点ではactual configを変更しない。

30. mail format
============================================================

Phase10 P0：

```text
plain text
UTF-8
HTMLなし
multipartなし
```

Content-Type：

```text
text/plain; charset=UTF-8
```

subject：

```text

二重encoding禁止
```

```text
base64
```

mail transport outputのline ending：

```text

```
