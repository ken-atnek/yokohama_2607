女の子詳細ページに次のボタンを設置する。

・本文中の女の子IDを使用しない
・本文中の店舗IDを使用しない
・本文が変更されても登録処理へ影響しない
・本文が削除されても登録処理へ影響しない

2.4 店舗ID

店舗IDは件名、本文、受付アドレスから決定しない。

件名から取得した女の子IDを使い、女の子マスターから取得する。

SELECT
    g_id,
    att_shop,
    view
FROM t_girl_master2
WHERE g_id = :cast_id
  AND view = '1';

att_shopを正式な店舗IDとする。

5. 登録者・購読フロー
============================================================

5.1 新規利用者

メールアドレスが新通知DBに存在しない場合：

1. Fromメールアドレスを取得する
2. 件名から女の子IDを取得する
3. 女の子の存在、view='1'、att_shopを確認する
4. suppressionを確認する
5. subscriberをpendingで作成する
6. subscriptionをpendingで作成する
7. verify_email delivery queueを登録する
8. Phase4ではraw token、verification URLを生成しない
9. Phase4では実メール送信しない
10. Phase10送信ワーカーが送信試行直前にraw token生成、token hash INSERT、URL生成、render/sendを行う
11. 利用者が認証確認画面を開く
12. 確認画面からPOSTする
13. subscriberをactiveへ変更する
14. subscriptionをactiveへ変更する
15. トークンを使用済みにする
16. 本登録完了メールを配信キューへ登録する

空メール受信だけではactiveにしない。

GETアクセスだけではactiveにしない。

5.2 認証待ち利用者

subscriber.status=pendingの利用者が別の女の子へ空メールを送った場合：

・既存subscriberを再利用する
・対象subscriptionをpendingで追加または再利用する
・既存unused verification tokenを必要に応じて無効化する
・verify_email delivery queueを登録する
・Phase4ではraw token、verification URL、実メール送信を行わない
・Phase10送信ワーカーが送信試行直前にraw token生成、token hash INSERT、URL生成、render/sendを行う

verify_email tokenはsubscription_id NOT NULLとし、1件のt_notification_subscriptionを指す。
本登録時は、当該token.subscription_idに紐づくpending subscriptionだけをactive化する。
同一subscriberに複数のpending subscriptionが存在しても、1つのverify_email tokenによる本登録で一括active化しない。
subscriber自体は正常認証完了時にactive化してよいが、他のpending subscriptionは自動active化しない。

5.3 認証済み利用者による女の子追加

subscriber.status=activeの利用者が別の女の子へ空メールを送った場合：

・再認証しない
・女の子検証を行う
・既存購読がなければactiveで追加する
・unsubscribedまたはpaused購読がある場合は業務ルールに従いactiveへ戻す
・「女の子を追加しました」メールを送信する
・監査ログを保存する

同じ女の子がすでにactiveの場合は重複行を作成しない。

5.4 delメール

del:<女の子ID>は新システムで受け付けない。

女の子単位解除と全登録解除は、設定画面からのPOSTだけで行う。

============================================================
8. 出勤通知対象
============================================================

8.1 通知対象

次の変更を通知対象とする。

・初回出勤登録
・出勤開始時刻変更
・休みへの変更
・休みから出勤への変更
・当日または翌日以降の予定変更

8.2 通知対象外

次の変更は通知しない。

・出勤終了時刻だけの変更
・TEL確認
・公休日
・LAST
・同じ内容の再保存
・過去日の修正
・リアルタイム設定の変更すべて

以前検討した以下のリアルタイム通知条件は廃止する。

・現在受付中
・残りわずか
・予約受付中
・指定時間変更
・待ち時間なし
・その他リアルタイム状態変更

8.3 日付条件

schedule_date < Phase8 event判定実行時のAsia/Tokyo基準today
・通知しない

schedule_date >= Phase8 event判定実行時のAsia/Tokyo基準today
・通知対象変更があれば通知イベントを生成する

ここでtodayは、schedule保存／event判定実行日のAsia/Tokyo calendar dateとする。

Phase9の「配信予定基準日以降の次回出勤日最大3件」とは別仕様であり、混同しない。

8.4 変更判定

更新日時だけで判定しない。

保存前と保存後の通知対象項目を比較する。

通知対象項目に差分がなければイベントを生成しない。

終了時刻だけが変わった場合はイベントを生成しない。

9.3 抽出範囲

単純に現在時刻から2時間前までを検索しない。

Phase9では、未処理pending eventをclaimed batch単位で処理する。

P9-03正式仕様として、以下を同一単位に固定する。

```text
1 Phase9 CLI invocation
= 1 claimed batch
= 1 notification InnoDB transaction
```

一度のCLI invocationで複数claimed batchを連続drainしない。

対象：

・status = pending
・available_at <= UTC_TIMESTAMP(6)
・Phase8が生成したschedule event

cron停止や一時障害があっても、次回実行で未処理分を回収する。

固定2時間wall-clock windowをmessage_group_keyへ使用しない。

batch sizeは `notification_delivery_create_batch_size` で指定し、1 Phase9 transactionでclaimする最大event数を意味する。

delivery row件数ではない。

batch上限を超えたpending eventは、次回Phase9 cron executionで回収する。

9.4 1通へまとめる単位

同じ利用者に複数の更新がある場合、1通へまとめる。

店舗をまたぐ場合も1通へまとめる。

delivery正式単位：

```text
1 row = 1 event × 1 subscription
```

同一メールにまとめる場合でも、eventごとのdelivery rowは全件作成する。

message_group_key：

```text
1回のPhase9 claimed batchで処理するevent集合のうち、
同一subscriberへ展開されるschedule_update delivery群
```

同一message_group_keyはPhase10 senderで1通として扱う。

mail-group専用tableは追加しない。

message_group_keyはBINARY(16)で、Phase9でrandom_bytes(16)により生成する。

同一message_group_key内は以下を同一とする。

・subscriber_id
・recipient_email_snapshot
・mail_type = schedule_update
・available_at

並び順：

1. 店舗
2. キャスト
3. 出勤日

9.6 次回出勤日3件

「3日分」は連続する3暦日ではない。

Phase9では、旧仕様の曖昧な送信日基準表現を直接使用せず、以下を正式基準とする。

正式基準名：

```text
配信予定基準日
```

正式定義：

```text
delivery.available_atをsubscriber.timezoneへ変換したcalendar date
```

配信予定基準日以降に登録されている次回出勤日を、日付順に最大3件表示する。

例：

配信予定基準日：
8月1日

対象キャストの次回出勤日：
・8月1日
・8月10日
・8月22日

通知メールには上記3件を表示する。

抽出条件：

schedule_date >= 配信予定基準日
かつ
canonical state = WORK

calendar dateごとに最大1件とする。

通常運用では、同一cast / 同一calendar dateに複数source rowが存在することは想定しない。

ただし異常・例外データとして同一calendar dateに複数rowが存在した場合、ORDER BY win ASCの最初のrowをそのcalendar dateの代表rowとする。

代表rowをcanonicalizeし、canonical WORKならnext_schedulesへ追加する。

WORK以外なら、そのcalendar dateはnext_schedulesへ追加しない。

同日の後続rowは採用しない。

これは正常データモデルとして同日複数rowを許容する仕様ではなく、異常データに対するP0 deterministic fallbackである。

除外：

P9-06 failure owner model：

```text
EVENT
TARGET
SYSTEM
WORK_DATA
INVARIANT / PROGRAMMING
UNKNOWN
```

EVENT failureは `EventDataValidationException` として明示し、EVENTのみpoison event isolationおよびrecordFailureAttempt対象とする。

raw `ValidationException` は一律EVENT扱いしない。

TARGET failureは `TargetPlanningException` として明示し、P0では `invalid_timezone` と `invalid_quiet_hours` を対象とする。

TARGET failure時は当該targetだけskipし、正常targetは処理継続する。batch全体rollback、event attempt_count増加、timezone fallback、subscriber自動修正、subscription pause、suppression自動追加は行わない。

TARGET counters：

```text

event_all_targets_invalid
```

`event_zero_target` はeligible/current target自体が最初から0件の場合のみを指し、`event_all_targets_invalid` と区別する。

SYSTEMはPDOExceptionとし、batch rollback、event attempt不消費、failure_event_idなしで扱う。

UNKNOWNはbatch rollback、failure_not_attributed、event attempt不消費とし、勝手にTARGET skipまたはevent failed化しない。
